# 2.0.0 career-agent-workbench-2-0-0-archive-flask-port

Release: `2.0.0`

Objective: Replace the reconstructed public Flask UI with the mature archived
Flask application as the behavioral, route, and visual source of truth, while
retaining the public repository's external-workspace, PII-exclusion, packaging,
operator-lifecycle, and human-review boundaries through narrow adapters.

## Operating Rules

- Follow root `AGENTS.md` before editing, validating, committing, pushing, or
  closing out release work.
- Treat this committed plan as the canonical workflow plan.
- Use runtime state in
  `tmp/agentic-workflows/career-agent-workbench-2-0-0-archive-flask-port/tracker.json`
  as the local cursor and evidence log, not as a second implementation plan.
- Treat P steps as implementation phases and G steps as reassessment gates.
- At each G step, compare completed work against the remaining plan and either
  continue, amend the future steps, or pause for user input.
- Gate amendments may change only incomplete/future work. Update this plan and
  the same-version changelog/release note together, commit normally, and rebind
  the ignored tracker to the new digest without rewriting completed history.
- Do not push, create or mutate a PR, merge, tag, publish, cut over operations,
  retire the archived fallback, call a provider/model, contact a third party,
  or mutate retained private application/profile/artifact state without
  separate explicit authority.
- Use fictional workspaces and fresh disposable database copies for validation.
  Store only sanitized hashes, counts, booleans, route names, and findings in
  Git or the ignored tracker; keep content-bearing evidence outside Git and
  delete it after its matching gate.
- The project-skills workflow standardization previously deferred to PR #3 is
  not part of this product migration unless separately authorized.

## Compatibility Principles

- Preserve the archived UI markup, styles, scripts, route semantics, labels,
  forms, progress presentation, editors, and navigation before considering any
  visual or architectural cleanup.
- Put public external-workspace resolution, CLI/operator compatibility, and
  schema translation at explicit boundaries around the imported app.
- Do not make the imported UI conform to the 1.2 reconstructed templates. The
  archive is the baseline; intentional deviations require gate evidence and a
  plan amendment.
- Do not copy the archived database, output tree, profile tree, dotenv, logs,
  downloads, generated documents, caches, or machine-specific settings.
- Do not reuse a mutated validation database. Every browser or mutation test
  gets a fresh disposable clone from a public-safe synthetic baseline.
- Preserve explicit resume selection, variant lineage, human-review gates, and
  the rule that the workbench never submits an application or contacts an
  employer.

## Steps

### P01 - Exact Archived Source Import

- Copy the bound source bytes exactly into a clearly named inactive public
  source module without importing or activating it.
- Record and test exact byte identity against the bound SHA-256 and line count.
- Add only the package-membership and documentation needed for the imported
  source to be reviewable; do not adapt imports, routes, templates, database
  access, configuration, or runtime behavior in this step.
- Verify the existing public webapp entrypoint and synthetic test suite remain
  unchanged and green.

### G01 - Import and Safety Reassessment

- Verify source identity, exact changed paths, public-tree safety, distribution
  membership, and absence of private state or machine paths.
- Inventory only interface-level activation blockers: package imports,
  `create_app`/CLI signatures, runtime paths, schema expectations, subprocess
  commands, and route collisions.
- Continue with P02 only if activation can be achieved through narrow adapters;
  otherwise amend future work or pause. Do not patch unrelated security or
  quality findings discovered outside the imported-app boundary.

### P02 - Public Runtime Adapter and Activation

- Make the imported archived app the active `career-agent-workbench-webapp`
  implementation with the smallest auditable mechanical namespace change and
  a thin public runtime adapter.
- Resolve the external workspace through the existing central configuration
  loader and pass exact database/output/template/download paths explicitly.
- Preserve the current PID-owned operator lifecycle and no-port-scan shutdown.
- Do not redesign or split the imported inline frontend in this phase.
- Add focused synthetic import, CLI, route-map, GET, and offline Chromium tests.

### G02 - UI and Runtime Reassessment

- Compare the activated public app against the bound archived source on fresh
  independent synthetic database clones and dynamic loopback ports.
- Require the archived layouts, controls, editors, action menu, progress panel,
  and navigation to remain materially identical. Record any unavoidable public
  workspace/config deviations explicitly.
- Exercise no provider/model/authenticated/application/employer action.
- Classify database/schema incompatibilities for P03 without broad patch loops.

### P03 - Database and Workflow Compatibility

- Repair only demonstrated incompatibilities between archived data access and
  the public state/workflow layer, favoring boundary adapters over UI rewrites.
- Preserve logical application state, variants, selected artifacts, ARO/CLO
  content, revisions, archive state, ATS fields, and background-stage semantics.
- Remove the superseded reconstructed templates/static/modules only after
  references and tests prove they are no longer active; retain reusable
  non-UI domain services where the imported app can call them safely.
- Add regression coverage for every compatibility repair with fictional data.

### G03 - Integrated 2.0.0 Release Readiness

- Run the complete synthetic suite, Ruff check/format, JavaScript syntax where
  applicable, Git diff checks, public-tree safety, wheel/sdist build and scan,
  isolated-wheel smoke, injected MCP stdio, and offline Chromium workbench.
- Compare the final public UI and representative safe workflows with the bound
  archived source using fresh disposable clones and sanitized evidence.
- Delete content-bearing evidence after review. Continue to PR preparation only
  if all invariants pass; PR publication, merge, tag, release, cutover, and
  archived-repository retirement remain separately authorized actions.

## Pause Conditions

- The bound archived source path or digest changes before exact import.
- Any copied path or content contains private profile/application state,
  generated artifacts, credentials, private environment values, or
  machine-specific paths.
- Activation requires copying the archived database, profile, output, dotenv,
  or another excluded private path.
- A compatibility failure would require redesigning the archived UI rather than
  a narrow runtime/state adapter.
- A validation failure invites unrelated security, deployment, or architecture
  remediation outside the current P step.
- Work would mutate retained private state, call a provider/model, access an
  authenticated service, submit an application, or contact an employer.
- PR #2 ancestry or the intended publication base changes and would make the
  stacked 2.0.0 history ambiguous.
- The next action requires push, PR, merge, tag, release, cutover, or fallback
  retirement authority that the user has not separately granted.
