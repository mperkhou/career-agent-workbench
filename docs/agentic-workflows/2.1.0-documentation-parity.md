# 2.1.0 career-agent-workbench-2-1-0-documentation-parity

Release: `2.1.0`

Objective: Bring the public documentation to relative parity with the mature
archived project documentation by replacing the intentionally tiny fictional
resume text and Master Resume Object (MRO) with a realistic, full-depth,
public-safe demo; rebuilding every README example from that approved demo; and
reassessing each diagram and Flask screenshot without exposing private career
state. Product work remains limited to the separately approved compatibility,
typed remote-API retry-contract, and additive sanitized-diagnostic compatibility
repairs needed to execute and explain the synthetic documentation workflow
safely.

## Operating Rules

- Follow root `AGENTS.md` before editing, validating, committing, pushing, or
  closing out release work.
- Treat this committed plan as the canonical workflow plan.
- Use runtime state in
  `tmp/agentic-workflows/career-agent-workbench-2-1-0-documentation-parity/tracker.json`
  as the local cursor and evidence log, not as a second implementation plan.
- Treat P steps as implementation phases and G steps as reassessment gates.
- At each G step, compare completed work against the remaining plan and either
  continue, amend incomplete/future work, or pause for user input.
- Gate amendments may change only incomplete/future work. Update this plan and
  the same-version changelog together, commit normally, and rebind the ignored
  tracker without rewriting completed history.
- Do not begin P01 until the user explicitly approves this initialized plan.
- Do not push, create or mutate a PR, merge, tag, publish, call a provider or
  model, fetch a new job posting, contact a third party, or mutate retained
  private profile, application, tracker, or generated-artifact state without
  separate explicit authority.
- Handle private source material read-only and outside the public repository.
  Never place original excerpts, private-source-bearing transformation drafts,
  mapping tables, screenshots, logs, or content-bearing evidence under the
  repository root, including ignored paths.
- Store only sanitized counts, ratios, hashes, booleans, route summaries, and
  findings in the ignored tracker. Keep sensitive or heavy evidence under
  `$TMPDIR/career-agent-workbench-agentic/career-agent-workbench-2-1-0-documentation-parity/`
  and delete it promptly after its matching gate.
- Use one main-agent owner for all private-source reading and candidate edits.
  Evidence routes may inspect only already-public candidates or content-free
  metrics; they must never receive the private source material.

## Anonymization Contract

- The public candidate must be a coherent fictional person and must be labeled
  as fictional wherever a reader could mistake it for a real profile. Use only
  reserved example domains and public-safe fictional contact data.
- Replace names, employers, titles, locations, schools, issuers, teams,
  customers, internal systems, product-specific identifiers, project names,
  URLs, dates where chronology could identify the source, and any unique
  combination that could link the candidate back to a real person or employer.
- Preserve the professional-skills taxonomy and technical substance as closely
  as safety permits. Generic skill names may remain; private aliases, internal
  tool names, and uniquely identifying groupings may not.
- For the single longest source role designated privately by the operator,
  preserve the long-form paragraph style and representative technical themes
  while reducing its paragraph/bullet count and source-word volume to roughly
  45-55 percent. Replace its employer, title, location, chronology, products,
  organizational references, and linkable phrasing.
- For every other role, retain the complete item count, approximate per-role
  depth, and substantive coverage. Do not trim content merely to simplify the
  demo; rewrite or generalize only as needed for fictional coherence and
  de-identification.
- Preserve the count, structure, and realistic feel of education, portfolio,
  and certification sections while replacing every identifying institution,
  issuer, project identity, repository identity, credential identifier, and
  link with coherent fictional equivalents.
- Keep dates, promotions, role ordering, locations, education, credentials,
  and portfolio history internally consistent after fictionalization.
- Do not send private text, distinctive phrases, or private identifiers to an
  internet search engine, external model, or evidence route. All source-to-demo
  comparison is local and content-hidden outside the main-agent workstream.
- Measure parity section by section. The designated long role must satisfy its
  45-55 percent target; other roles must preserve their source item counts and
  remain within a reasonable per-section word-volume band unless privacy
  requires a documented exception. Git and tracker evidence records only the
  ratios and pass/fail result, never the source values or mapping table.

### P03D - Typed API Retry and Additive Diagnostic Repair

- Treat P03C/G03C as completed historical evidence of the then-implemented
  timeout-only workflow contract. Do not rewrite those completed results or
  any retained P03R attempt. The corrected P03R run established one narrower
  defect: API-backed v1/v2 workflows own a visible retry budget but retry only
  `ModelTimeoutError`, while their one-attempt workflow API client collapses
  other provider failures into generic `LlmError`. Repair that demonstrated API
  path prospectively; do not claim provider-agnostic transient-retry parity.
- Keep the v1/v2 workflow layer as the single retry owner for every API-backed
  logical operation. A configured `retry_count` permits at most
  `retry_count + 1` provider boundaries including the initial request. Keep
  workflow-created API clients at one internal attempt, while preserving any
  compatible direct-client behavior outside that construction path. Do not
  broaden manual-pass or highlighting Codex retries. Keep non-timeout Ollama
  failures non-retryable in 2.1.0; its existing typed-timeout behavior remains
  unchanged and must be documented honestly.
- Define typed retryable and non-retryable API/model failures rooted
  compatibly in `LlmError`, with `ModelTimeoutError` remaining a distinct typed
  timeout marker. Classification must use type and validated closed metadata,
  never exception-message parsing. Exception messages and structured metadata
  must be content-free, and diagnostics must never serialize tracebacks, raw
  exception messages, prompts, outputs, response bodies, credentials, URLs,
  paths, private headers, or provider-private text. A validated numeric HTTP
  status and bounded delay value may be retained only for the closed contract.
- Retry only HTTP 408, 409, 425, 429, 500, 502, 503, and 504; sanitized remote
  connect, read, and protocol interruptions that are reasonably transient;
  valid supported API envelopes containing an empty generation; and the
  existing typed timeout. Preserve bounded exponential backoff and bounded
  `Retry-After` handling without retaining raw headers or creating nested
  attempts. Cap accepted `Retry-After` timing at 120 seconds and fallback
  exponential backoff at 60 seconds.
- Keep permanent HTTP failures, malformed or unsupported envelopes, response-
  size violations, syntactically invalid generation JSON, valid-JSON schema or
  application rejection, unexpected model failures, and evidence/policy/state/
  render/ATS/local-path/artifact failures non-retryable. For v2, classify
  syntactically invalid generated JSON before reporting the logical operation
  complete; leave schema and application validation after valid JSON outside
  the retry loop.
- Preserve every broad diagnostic category, including `category=model`, and
  add only an optional validated `failure_subtype`. The closed subtype
  vocabulary remains `timeout`, `transient_http`, `permanent_http`,
  `transport_read`, `transport_protocol`, `transport_connect`,
  `empty_completion`, `malformed_envelope`, `invalid_generation_json`,
  `response_too_large`, and `unexpected_model`. Existing P03C/P03R events and
  status records without a subtype must remain readable; do not rewrite or
  delete retained history.
- Use the existing P03C stderr event stream and Flask-owned bounded action log.
  Emit content-free stage, attempt N/M, elapsed time, broad category, optional
  subtype, and retry decision events so the next separately authorized single-
  job traversal can distinguish a transient retry, exhaustion, and an immediate
  non-retryable failure. Direct CLI remains stderr-only for these events and
  Make remains a command composer. Do not add a direct/Make durable recorder,
  run IDs, leases, cross-process ownership, restart recovery, multi-job
  correlation, truncation aggregation, durable final summaries, a structured
  viewer, or composite-Make ownership semantics in 2.1.0. Those form one
  deferred feature architecture; leave the committed P03C Flask persistence
  behavior intact.
- Add focused mocked/fake tests for 429 then success; 502, 503, and 504 then
  success; transient connect/read/remote-protocol interruption then success;
  empty completion then success; timeout then success; exhausted transient
  attempts; permanent 400, malformed envelope, response-too-large, invalid-
  generation JSON, and unexpected failures without retry; v2 parity; and exact
  provider-boundary counts that never exceed `retry_count + 1`. Prove the
  workflow API client has one internal attempt, legacy diagnostics without a
  subtype still load, subtype classification is independent of raw exception
  text, and diagnostic output excludes prompts, responses, keys, URLs, paths,
  raw exception text, job IDs, and private content. Preserve focused tests for
  unchanged Ollama timeout and manual/highlighting behavior.
- Keep direct CLI/Make path handling compatible and include every retained new
  module/test in the explicit source distribution membership. Align the
  retained `2.1.0` version, `CHANGELOG.md`,
  `docs/release-notes/2.1.0.md`, and README operational text with the verified
  API-specific contract without claiming a successful live traversal.
- Keep P03D completely offline: do not resolve the private dotenv, invoke a
  provider/model or Codex subprocess, mutate the retained synthetic workspace,
  or consume renewed P03R authority. Preserve the deterministic demo, P03R
  workspace, four empty mode-0700 snapshot directories, completed commits, and
  tracker history.
- Run the focused and proportional regression suites, Ruff check/format,
  `git diff --check`, public-tree safety, and a deliberate privacy/scope review.
  Commit P03D normally and stop at G03D with a clean worktree. Do not bundle or
  authorize another force-v1 traversal.
