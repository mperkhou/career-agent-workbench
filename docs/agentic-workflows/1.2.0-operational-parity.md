## Operating Rules

- Follow root `AGENTS.md` before editing, validating, committing, pushing, or
  closing out release work.
- Treat P steps as bounded implementation phases and G steps as functional
  reassessment gates. Use exactly `P01/G01`, `P02/G02`, and `P03/G03` for the
  approved scope unless a gate authorizes a narrowly scoped `Pnn-Rn` repair.
- Record `begin` before a dispatched P step mutates files. Record sanitized
  evidence before marking a P step complete or assessing its G gate.
- Preserve normal reviewed commits. Repairs append commits; do not amend,
  rebase, squash, reorder, reset, or force-push reviewed history.
- The planner may amend only incomplete/future work. An amendment updates this
  plan and the same-version changelog entry together, is committed normally,
  and is followed by an explicit tracker rebind.
- Do not push, open or mutate a PR, merge, tag, publish, deploy, contact an
  external party, retire the legacy fallback, or perform operational cutover
  without fresh explicit user authority.
- Do not make provider/model calls, authenticated LinkedIn requests,
  application submissions, employer contact, or private application-state
  mutations as part of validation.
- Keep real profile data, identifiers, dotenvs, databases, artifacts, raw
  logs, screenshots, and content-bearing evidence out of Git. Small sanitized
  control evidence may live beneath the ignored workflow runtime directory;
  heavy or sensitive evidence belongs under a disposable system temporary
  directory.
- Evidence routes are read-only. They may inspect only the declared code,
  synthetic fixtures, disposable validation results, or content-free
  aggregates and may recommend `continue`, `amend`, or `pause`; they cannot
  authorize changes.
- Gates assess the authorized functional behavior. They do not broaden into a
  generalized security review, architecture redesign, legacy monolith
  restoration, pixel-parity exercise, deployment project, or unrelated UI
  rewrite.

### Functional Acceptance Criteria

- `I2`: Add and Seed expose optional dependent v1, v2, manual-profile, and
  highlighting composition at ingestion time. Invalid dependency combinations
  fail content-free before execution. Each successfully ingested job enters
  only the selected downstream stages; a per-job or per-stage failure is
  recorded without preventing surviving jobs from continuing. Existing
  standalone actions remain available, and no new provider or model route is
  introduced.
- `A2`: sync-selected-draft-to-ARO no longer requests a state-store page above
  the supported maximum. The same bounded synthetic/disposable operation
  succeeds through the direct script, its Make target, and the Flask action,
  while preserving revision/selection semantics and content-free failures.
- `A3`: the local UI prefers the active run, shows compact live stage/job
  progress with a progress indicator and bounded message list, and supports
  collapse and dismissal. Partial batches identify retryable failed jobs or
  stages without persisting content, exception text, paths, or credentials.
  Retrying failed work does not repeat completed survivor work unless the
  operator explicitly requests it.
- `V2`: each variant review uses its declared parent and presents the actual
  implementation-neutral comparison, ARO/ATS differences, accepted/rejected
  evidence summaries when present, and bounded review metadata/timestamps.
  Missing optional evidence is explicit rather than fabricated, and no raw
  provider traffic or private values are exposed.
- Existing selection/reset, artifact download, ingestion, action allowlist,
  state isolation, and public-only fetch invariants remain green.

### Evidence And Proportional Validation

- Focused synthetic tests cover dependency validation, survivor execution,

- A disposable ops-dev browser route exercises one successful composite, one

### Functional Acceptance Criteria

- `C2`: the editor provides a bounded rendered rich-text surface and preview
  for ordinary paragraph, line-break, bold, italic, and safe-link editing.
  Toolbar actions have accessible semantics, the stored submission passes
  through the existing server-side sanitizer, unsafe markup never executes or
  persists, and the current transactional save/render/copy/download contract
  remains intact.
- Operators can inspect or recover the sanitized source without hand-authoring
  HTML for normal edits. Preview and submitted HTML remain deterministic and
  faithful to the allowlisted formatting only.
- `C3`: the established unchanged representative 511-word/3,844-character
  letter renders on one Letter page with professional readable typography and
  margins, exact normalized text preservation, and no clipping or overlap.
  Determinism, safe-link formatting, maximum-size bounds, and failure atomicity
  remain green. Layout is not compressed solely to game the page count.
- Existing cover-letter state isolation, explicit artifact views/downloads,
  configured copy behavior, and content-free failures remain unchanged.

### Evidence And Proportional Validation

- Focused tests cover toolbar/source synchronization, sanitizer enforcement,
  preview fidelity, transactional failure, PDF determinism, exact extracted
  text, one-page representative output, and clipping/overflow bounds.
- A read-only rendered-layout route compares sanitized public and legacy
  geometry for the representative letter without recording its content.
- A disposable ops-dev browser route exercises rich editing, preview, save,
  rerender, artifact view/download, and configured copy using a disposable
  workspace and sanitized evidence.
- Run Ruff check/format on changed Python, `git diff --check`, focused tests,
  public-tree safety, and the existing cover-letter artifact regressions.

### P03 Pause Conditions

- One-page output requires illegible typography, content loss, unsafe markup,
  or removal of established letter text.
- Rich editing requires a new unreviewed client dependency, weakens the server
  sanitizer, or creates a second persistence model.
- Disposable validation fails state-isolation or private-data boundaries.
- An unlisted path or broader renderer rewrite is required.

G03 first assesses `C2` and `C3`, then reassesses all nine approved IDs against
the exact workflow branch and accepted evidence. It must confirm:

- P01, P02, and P03 focused suites and regression invariants pass;
- Ruff check and format, `git diff --check`, and public-tree safety pass;
- the complete synthetic suite passes;
- wheel and sdist build/scan, isolated-wheel smoke, offline Chromium,

- disposable ops-dev feature/browser checks pass without private evidence in

- a bounded, content-free, read-only full-ops aggregate check confirms schema,
  counts, hydration, selection, lineage, and cutover compatibility without
  exposing values or mutating the retained workspace.

G03 records `continue`, `amend`, or `pause`. Any repair is append-only and
narrowly tied to a failed approved capability or release-readiness invariant.
Even after a technical pass, the workflow remains paused for explicit user
authority before push, PR creation or mutation, merge, tag, release,
operational cutover, or legacy retirement.

## Global Pause Conditions

- The tracker binding, plan digest, revision, branch, bootstrap commit, or
  entrance baseline does not match.
- Remaining work no longer matches the nine approved capability IDs or needs a
  path outside the current P-step boundary.
- Validation failure requires a broader refactor, migration, security phase,
  provider change, or architecture project.
- A step risks live tracker data, generated artifacts, credentials, private
  content, retained full-ops state, or the frozen legacy/PR #1 evidence.
- A requested action would push, open or mutate a PR, merge, tag, publish,
  deploy, contact a third party, cut over operations, or retire the fallback
  without explicit current authority.
- Required evidence is missing, private, content-bearing, contradictory, or
  cannot be obtained from a disposable or read-only route.

## Completion Definition

This implementation workflow is technically complete only when G03 has
accepted all nine capabilities and all release-readiness evidence against the
exact branch history. Technical completion does not itself authorize release
or cutover. The legacy application remains the operational fallback until a
separate explicit cutover decision, and the workflow remains paused at every
external-state or release boundary.
